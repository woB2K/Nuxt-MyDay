# Сверка копилки — дизайн

## Зачем

После крупных движений денег (продажа машины, покупка новой) баланс копилки в приложении разошёлся с реальностью. Нужно сказать «по факту у меня сейчас X», чтобы баланс стал правильным, а история прошлых месяцев осталась как была.

## Цели / не-цели / анти-цели

- **Цель:** одной операцией привести баланс к реальной сумме, история до сверки нетронута.
- **Не-цель:** «эпохи» и отсечение старых записей из баланса; бэкдейт сверки.
- **Анти-цель:** сверка не должна выглядеть как пополнение/снятие — не портит «+N за месяц» (delta) и прогресс целей.

## Подходы

- **A. Тип записи `ADJUSTMENT` (выбран).** Сервер считает разницу между фактом и текущим балансом и пишет её отдельной записью. Простой, история цела, с семейной копилкой без вопросов.
- **B. Несколько `OPENING` («эпохи»).** Отвергнут: стартовый остаток — у каждого автора свой, неясно, чей сброс отсекает чьи записи; ломает инвариант «один OPENING», restore и цели.
- **C. Обычное снятие/пополнение на разницу.** Отвергнут: искажает delta за месяц — ровно то, от чего уходим.

## Решения

- `SavingsType` += `ADJUSTMENT`, миграция. **`amount` у сверки — со знаком** (единственное исключение из «amount всегда положительный»; фиксируем в `ARCHITECTURE.md`). *Моё решение:* один тип со знаком проще, чем пара `ADJUST_UP/DOWN`.
- Баланс = `OPENING + DEPOSIT − WITHDRAWAL + ADJUSTMENT`. Обновить все места подсчёта: `savings/index.get.ts`, `invite.ts`, `householdView.ts` (`members[].savingsBalance`), `financeCache.ts` (оптимистичное удаление).
- **Delta за период и прогресс целей сверку не учитывают.** К цели сверку не привязать.
- **API:** `POST /api/finance/savings/reconcile { actual }` — не CRUD, клиент сумму разницы не присылает. Сервер в `$transaction` считает **свою часть** баланса (`householdId` + `userId`, `deletedAt: null`) и создаёт запись на разницу. Разница 0 → 400 «баланс уже совпадает». `actual` ≥ 0, ≤ `MAX_AMOUNT`, Zod-схема в `shared/schemas/finance.ts`. `ADJUSTMENT` через обычный `POST /savings` создать нельзя.
- **Семья:** сверяется всегда только своя часть — те же суммы, что `members[].savingsBalance`. Человек знает факт только по своим деньгам; записи и доля партнёра не трогаются. При раздельной копилке своя часть = весь баланс, поэтому правило одно для обоих режимов. При общей копилке шторка подписывает «Твоя часть в приложении · Y», общий баланс меняется ровно на разницу.
- **Редактирование:** сверку не редактируем (PATCH → 400). Удаление — обычный soft delete с корзиной и undo; ошиблись → удалить и сверить заново. *Моё решение:* «стало X» после чужих правок задним числом не пересчитать честно.
- **UI:** там, где сейчас «Указать стартовый остаток», когда остаток уже есть — ссылка «Сверить баланс» (иконка `i-lucide-scale`). Открывает `SavingsOpSheet` в режиме `ADJUSTMENT`: поле «Сколько сейчас по факту», под ним «Сейчас в приложении · Y» и превью «Разница · ±Z». Кнопка «Сверить».
- **История:** строка с иконкой scale, нейтральный тон (accent-soft, как OPENING), сумма со знаком, подпись «Сверка · дата». Сумма через `UiMoney`.
- i18n `en` + `ru`.

```
┌ Сверить баланс ───────────────┐
│        380 000 ₽              │  ← ввод факта
│  Сейчас в приложении 1 240 000│
│  Разница  −860 000 ₽          │
│  [ Заметка                  ] │
│  [        Сверить           ] │
└───────────────────────────────┘
```

## Тесты

- Интеграционные: сверка вверх/вниз, разница 0 → 400, delta периода её не включает, общая/раздельная копилка, PATCH → 400, удаление/restore, `ADJUSTMENT` через `POST /savings` → 400.
- Unit: схема `reconcile`, `savingsLooks`.
